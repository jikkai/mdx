`@amamo/mdx` is an MDX content compiler. A Rust core parses MDX, validates frontmatter, compiles
JSX, and renders code blocks; the same compiler state powers the root API, the Vite 8 plugin, and
the Next 16 wrapper. The same input, the same output, on every surface.

```sh
pnpm add @amamo/mdx
```

## What it does

- **Rust core** parses MDX, runs frontmatter through a JSON Schema, and emits JavaScript modules with
  source-position mappings.
- **Official Shiki** highlights code blocks. The default engine is the Oniguruma WASM build; the
  JavaScript engine is also supported.
- **Media imports** rewrite relative URLs in Markdown into static imports, with attributes derived
  from the HTML tag.
- **Deterministic manifests** project the public frontmatter, the protected status, and a
  content hash for every document.
- **Content-addressed cache** stores compiled records by a hash of the input bytes, the config
  fingerprint, and the Shiki version, so unchanged sources are never rewritten.

## What it does not do

- It is not a runtime. The compiler writes JavaScript modules to disk and returns them; rendering
  is the host's responsibility.
- It is not a sandbox. MDX can contain executable JavaScript; only compile content from authors you
  trust.
- It is not a content management system. Manifests project fields; they do not author them.

## Three surfaces, one compiler

| Surface  | Import            | Use it when                                                |
| -------- | ----------------- | ---------------------------------------------------------- |
| Root API | `@amamo/mdx`      | You want to drive the compiler directly from a script.     |
| Vite 8   | `@amamo/mdx/vite` | You are building a Vite app that owns its own content.     |
| Next 16  | `@amamo/mdx/next` | You are building a Next app and want the same content set. |

The Vite and Next adapters run the same `IAdapterCompiler`; the only difference is who owns the
file watcher and the generated module.
