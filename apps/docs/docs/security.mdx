# Security model

`@amamo/mdx` does not classify or encrypt frontmatter fields, and it does not make untrusted MDX
safe. Treat the author, configuration module, generated files, and deployment destination as
separate trust boundaries.

## MDX is executable

MDX can contain ESM imports and JavaScript expressions. The compiler emits them into a JavaScript
module, and the host may execute that code during bundling, import, server rendering, or client
rendering.

Compile only content from authors you trust to run code with the host application's privileges.
JSON Schema validates frontmatter data; it does not inspect or sandbox the MDX program.

## Frontmatter is ordinary data

After schema defaults and validation, the complete frontmatter object is exported by the compiled
MDX module and stored in document records, cache records, and the generated collection registry.
Configured manifests contain the fields that they project. There is no field-level redaction,
encryption, or decryption.

To protect a value, store ciphertext in an ordinary frontmatter field and decrypt it in the
consumer, or keep the value outside frontmatter. Do not store the encryption key in the same content
or generated output.

## Diagnostics can contain submitted values

Schema validator messages may quote an invalid submitted value. Do not return raw compiler errors
or build logs to an untrusted author.

Successful warning diagnostics are stored on the document record. The compiler and Vite plugin do
not automatically log them, so the caller controls where they are exposed.

## Manifest projections

Any frontmatter source can use these transforms:

```ts
fields: {
  categoryPresent: { from: 'category', transform: 'exists' },
  categoryFingerprint: { from: 'category', transform: 'sha256' },
}
```

- `exists` reveals only whether the value is present and non-null.
- `sha256` emits a deterministic, unsalted digest.

Raw SHA-256 is not encryption or a password hashing function. A transform also does not hide the
original frontmatter value from compiled modules, records, or caches. Use consumer-managed
encryption for protected values and a dedicated password KDF and authentication system for human
passwords.

Manifest names such as `public` or `server` carry no access-control semantics. The compiler writes
the configured file; your deployment must decide whether that path is public.

## Markdown media containment

On a fresh compilation, relative media generated from Markdown is normalized against the source
file, checked against `root`, canonicalized when it exists, and rejected if a symlink resolves
outside the canonical root. External, absolute, fragment, protocol-relative, and data URLs pass
through without this local-file check. Authored MDX JSX is not rewritten.

A warm cache hit checks that the dependency path recorded by the earlier compile still exists. It
does not recanonicalize a media symlink whose target changed while the MDX source and config stayed
unchanged. After changing symlink targets, remove the affected cache or run with caching disabled
while the target may change. A single cache-disabled build checks fresh paths but does not replace
the old cache entry.

The manifest-only `mediaUrl` transform is different: it lexically maps a relative value to a
root-relative URL. It neither checks file existence nor creates an import.

## Configuration is data after import

Normalization rejects functions, accessors, symbols, class instances, cycles, non-finite numbers,
and other non-JSON-like values. This makes the normalized value reproducible enough to fingerprint,
but it does not sandbox the JavaScript or TypeScript configuration module that creates that value.

Fingerprints use serialized normalized data. Object key order therefore affects the fingerprint and
may produce a cache miss even when two objects are otherwise equivalent.

## Cache and output writes

Cache records contain complete validated frontmatter, derived data, projections, dependencies,
diagnostics, and the compiled module. Highlighted output is part of the same record; there is no
separate disk highlighter cache.

Cache, manifests, and the three shared generated files may live in different configured directories.
Protect those paths according to their contents instead of assuming everything is under
`generatedDirectory`.

Shared generated files and manifests compare existing bytes before writing. They and cache records
use same-directory temporary files plus rename for complete-file replacement; cache records do not
run the TypeScript byte comparison. Readers should see the old complete file or the new complete
file rather than a partially written record.

## Deployment checklist

- Only trusted authors can change MDX or its imports.
- Protected values are encrypted before entering frontmatter or kept outside it.
- Raw validation errors are not exposed to untrusted users.
- No manifest containing private metadata is deployed to a public path.
- Symlink target changes force a fresh media compilation.
- Authentication and password storage remain outside frontmatter and manifest SHA-256 projections.
