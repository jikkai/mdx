# Native targets

The published package loads one napi-rs binary selected from the current operating system,
architecture, and Linux libc. No JavaScript or WASI implementation is bundled.

## Supported targets

| Rust target                  | Platform package              | Runtime           |
| ---------------------------- | ----------------------------- | ----------------- |
| `aarch64-apple-darwin`       | `@amamo/mdx-darwin-arm64`     | macOS arm64       |
| `x86_64-apple-darwin`        | `@amamo/mdx-darwin-x64`       | macOS x64         |
| `aarch64-unknown-linux-gnu`  | `@amamo/mdx-linux-arm64-gnu`  | Linux arm64 glibc |
| `x86_64-unknown-linux-gnu`   | `@amamo/mdx-linux-x64-gnu`    | Linux x64 glibc   |
| `aarch64-unknown-linux-musl` | `@amamo/mdx-linux-arm64-musl` | Linux arm64 musl  |
| `x86_64-unknown-linux-musl`  | `@amamo/mdx-linux-x64-musl`   | Linux x64 musl    |
| `x86_64-pc-windows-msvc`     | `@amamo/mdx-win32-x64-msvc`   | Windows x64       |

## When the binding loads

`createCompiler()` normalizes the config and may initialize Shiki without loading Rust. The first
`build()` or `transform()` enters `prepareNativeBatch`, which then requires `native.cjs` and the
matching binary.

The loader tries a local `index.<platform>.node` first, then the corresponding platform package. A
platform package must have the exact same version as the root package.

| Top-level error            | Meaning                                                             |
| -------------------------- | ------------------------------------------------------------------- |
| `AMAMO_NATIVE_UNSUPPORTED` | The OS or CPU has no known target mapping.                          |
| `AMAMO_NATIVE_UNAVAILABLE` | The target is known, but neither local nor packaged binding loaded. |

A package version mismatch appears as `AMAMO_NATIVE_VERSION_MISMATCH` inside the
`AMAMO_NATIVE_UNAVAILABLE` aggregate cause, not as the top-level loader error.

If installation succeeded on another machine, reinstall dependencies on the current target. Package
manager caches are safe; a copied `node_modules` directory is not.

## Node.js policy

The root and platform packages declare Node.js `>=20.19`. Repository CI currently runs the complete
quality gate on Node.js 24, then builds the Next fixture with Turbopack and Webpack. Treat 20.19 as
the supported engine floor, not a claim that every intervening release is exercised in CI.

The native crate enables N-API 8.

## Shiki engines are separate

The native target does not select the highlighter engine. Configure Shiki independently:

```ts
highlight: {
  provider: 'shiki',
  engine: 'oniguruma', // or 'javascript'
  themes: { light: 'vitesse-light', dark: 'vitesse-dark' },
}
```

Both values use Shiki's official engine implementations. Test your actual language and theme set
before switching; this package does not promise byte-identical output between engines.

## Build locally

The repository pins Rust in `rust-toolchain.toml`. On a supported development machine:

```sh
pnpm install
pnpm run build:native
node scripts/check-artifacts.mjs --local native.cjs
```

`build:native` builds the current platform binding and generates `native.d.ts`. `pnpm test` rebuilds
both native and TypeScript output before running the integration suite.

Adding a target requires more than passing `--target`: update the napi target list, native loader,
platform package, artifact validator, release matrix, and target-native load verification.

## Release verification

The release workflow builds and load-tests each native artifact on its matrix runner (or Alpine for
musl). The publish job then runs the full quality gate, validates all downloaded package artifacts,
dry-runs every npm package, and publishes platform packages before the root package.
